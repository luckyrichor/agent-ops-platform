## 1. 现状与基线

- 商品目录在 `commerce.products`（P2 合成 20 万行），检索走 `CatalogSearch`：PostgreSQL 全文（`to_tsvector('english', title)`）+ 类目/价格/属性/库存过滤，无缓存。
- 已有证据：P7 检索样本里中文“电水壶”0 命中；说明当前分词对中文无效。**这不是 S3 的稻草人，而是产品当前的真实做法**，S3 基线就是它。

基线定义：产品当前的数据库索引检索，**不先加“无索引全表扫”这种人造基线**。所有提升相对当前检索路径比较。

## 2. 前置（必须先做，做完才跑 S3）

### a. 中文检索修复

- 数据：给合成商品补中文 `title_zh`、`description_zh`（固定种子、可复现）；不改真实用户数据。
- 索引：采用字符二元组/三元组（`pg_trgm` 或等效）或中文分词扩展；先验证 `pg_trgm` 在本机可用与索引体积，再选型。
- 样例：至少覆盖“电水壶”“保温杯”“无线鼠标”“退货运费”等查询，命中集必须非空且有据可查。
- 验收：给定 30 条中文查询，每条前 5 结果人工可判定相关；不能只证明“有返回”。

### b. 无模型检索基准

- 独立脚本，不走 planner、不调用任何模型；只测检索路径：查询→召回→过滤→排序→返回。
- 指标：QPS、p50/p95/p99、召回@10（对固定标注查询集）、DB QPS 与连接等待。
- 数据：固定查询集 + 固定商品快照；环境指纹与每轮重置沿用 S1/S2 做法。

### c. 访问分布检查

- 真实访问分布与合成请求分布在 **1% 与 10% 缓存容量**下的命中率差距。
- 真实数据：P2 UserBehavior 或 ECD 浏览记录（只统计类目/商品频次，不导出原文）。
- 判据：两档命中率差距都 ≤5 个百分点；超过就先修生成器（Zipf 参数/类目权重），修完再进 S3。检查结果写入 `S3.md`，并说明命中率是在合成分布上的结果。

## 3. 假设（方向，不写数字）

1. 进程内 LRU（短 TTL）对热商品能降低读 p99，但跨进程命中率有限。
2. Redis 共享缓存能提高多实例命中率，代价是多一次网络往返与失效复杂度。
3. 同一键并发回源合并（singleflight）能削掉击穿峰值；代价是首个请求延迟略增。
4. 空值缓存能防穿透，但会放大“新上架商品短暂不可见”的窗口。
5. “先写库再删缓存 + 版本号回填”能把过时读压到可接受窗口；只删缓存或延迟双删会留下更长窗口。

失效条件：缓存键漏掉版本/类目维度；TTL 抖动不足导致同时过期；singleflight 把不同请求体合并；库存扣减路径被缓存；过期回填覆盖新版本。

## 4. 改动（逐层单独测）

1. 进程内 LRU，短 TTL（秒级）。
2. Redis 缓存，TTL + 随机抖动。
3. singleflight 合并同键回源。
4. 空值缓存（短 TTL）。
5. 写路径：先写库、再删缓存；缓存值带版本号，旧版本回填被拒。

## 5. 实验矩阵

- 缓存容量 1% 与 10% 两档；请求分布用前置 c 校验过的合成分布。
- 基线（无缓存）与每一层分别 5 轮，同轮 A/B 交替；A/A 5 轮求噪声。
- 一致性复现：脚本制造“读并发于写”，分别在只删缓存 / 延迟双删 / 版本号回填三种策略下统计过时读比例。
- 指标：分层命中率、读 p50/p95/p99、DB QPS、过时读比例、热键过期瞬间回源峰值、内存占用。
- 判据：提升需同时超过 10% 与 A/A 噪声较大者，否则写“无显著收益”。

## 6. 正确性门槛

- 库存扣减路径不得读缓存。
- 过时读比例必须可量化并有上限；不能只报平均值。
- 缓存不可用时（Redis 断连）必须回源且不返回错误；降级行为要有测试。
