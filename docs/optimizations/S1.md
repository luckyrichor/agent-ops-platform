# S1 百万工单待处理队列与抢单

2026-11-03，Codex。实验数据：`docs/measurements/2026-11-03-s1/`（`summary.json` 为机器汇总）。预期原文：[S1-expectation.md](S1-expectation.md)。

## 1. 现象

50 个座席从 100 万工单里领取“待人工”工单，同时 20 个工作台客户端翻页。基线（产品 CAS + OFFSET、无队列索引）在 100 万行时，单次领取 p95 8.3 秒、第 2500 页 p95 9.6 秒、吞吐 3.7 次/秒；座席大部分时间在等全表扫描与抢锁冲突。

## 2. 假设与验证

| 假设 | 结果 |
| --- | --- |
| 部分索引降低扫描与索引体积 | 成立：索引 2.44 MB（主键 39.5 MB），建索引 0.23 秒 |
| keyset 消除深翻页线性增长 | 成立：第 2500 页 p95 9.58 s → 53 ms |
| SKIP LOCKED + 版本号提升领取吞吐、重复为 0 | 部分成立：组合吞吐 3.74 → 245.9 次/秒；但消融显示主要贡献来自 keyset 与索引，SKIP LOCKED 单独仅 7.1 次/秒 |

## 3. 改动

- `CREATE INDEX CONCURRENTLY s1_queue_partial ON support.tickets (priority DESC, created_at, ticket_id) WHERE state='waiting_human'`。
- 列表改 keyset：`WHERE (priority, created_at, ticket_id) < (…) ORDER BY … LIMIT 20`；第 1 页无游标。
- 领取改单条 `UPDATE … WHERE ticket_id = (SELECT … FOR UPDATE SKIP LOCKED LIMIT 1) AND state='waiting_human' RETURNING …`，版本号 `revision` 保持 CAS 语义。

产品默认 CAS 未改；B 与 N 都只在实验脚本里。

## 4. 结果

数据：100 万工单、5% 待人工（5 万）、50 座席、20 个列表客户端、每轮 60 秒；W2 思考时间 0，供给不足时每 0.5 秒把 1 秒前领取的行重置回待人工。

**A/A 噪声**：10 次 A 基线，吞吐 3.38–3.89 次/秒，spread **13.75%**，故判据阈值取 13.75%（大于 10%）。

| 指标（中位） | A 基线 | B 优化 | 变化 |
| --- | ---: | ---: | --- |
| 领取吞吐（W2，主指标） | 3.74 次/s | 245.88 次/s | 每轮配对 59.8–67.2 倍，中位 **62.0 倍** |
| 领取 p95 | 8,346 ms | 89.6 ms | −98.9% |
| 第 2500 页 p95（第二主指标） | 9,584.6 ms | 53.1 ms | 比值 0.0058（−99.4%） |
| 重复领取 | 0 | 0 | 门槛满足 |

5 轮配对比值：62.0 / 59.8 / 62.0 / 66.3 / 67.2，全部远超阈值 13.75%。

**消融（各 3 次，中位）**

| 配置 | 吞吐 次/s | 领取 p95 | 第 2500 页 p95 |
| --- | ---: | ---: | ---: |
| A 基线（无索引 + OFFSET + CAS） | 3.74 | 8,346 ms | 9,585 ms |
| 只开 keyset（无索引） | 409.4 | 50.6 ms | 28.5 ms |
| 只开部分索引（OFFSET） | 231.2 | 92.2 ms | 572.3 ms |
| 只开 SKIP LOCKED（无索引） | 7.1 | 10,090 ms | 9,071 ms |
| B 组合 | 245.9 | 89.6 ms | 53.1 ms |

结论：深翻页几乎完全由 keyset 决定（索引单独只能到 572 ms）；领取吞吐由“索引 + keyset”共同抬高。**B 的吞吐低于只开 keyset**（245.9 vs 409.4），原因是部分索引在每次领取时维护（行离开索引）且 SKIP LOCKED 多一次子查询；这是用吞吐换“无冲突领取”的代价，报告不隐瞒。由于本实验里 A 的重复领取已经是 0，SKIP LOCKED 在正确性上没有额外收益，只在冲突率高的场景有意义。

**朴素两步领取（只演示，不参与提升倍数）**：997.4 次/秒，但三次共 **101,715 次重复领取**（每轮约 3.4 万，占领取数约 57%）。它说明“快但错”的路径确实存在，也说明 A 的产品 CAS 不是两步领取。

**W1 真实节奏（思考 2 秒 ±200 ms，辅助）**

| 指标 | A | B |
| --- | ---: | ---: |
| 领取吞吐（中位） | 3.27 次/s | 24.38 次/s |
| 领取 p50（中位） | 4,076 ms | 6.5 ms |
| 领取 p95（中位） | 6,072 ms | 10.6 ms |
| 第 2500 页 p95 | 7,347 ms | 8.2 ms |

B 达到思考时间决定的上限 25 次/秒；A 因 4 秒级查询远低于上限。W1 只作辅助，不用来判断优化收益。

## 5. 代价与失效条件

- 部分索引要求查询谓词与 `state='waiting_human'` 完全一致；改成别的状态或加 `OR` 会退化为全表。
- keyset 依赖 `(priority, created_at, ticket_id)` 稳定；`priority` 变更会让正在翻页的客户端跳项或重复。
- SKIP LOCKED 不保证公平与优先级严格顺序，低优先级工单可能饥饿；本轮 60 秒窗口内未观察到饥饿，但不能外推。
- 索引维护使领取写入变慢：B 吞吐低于只开 keyset 的 409.4 次/s。
- 本实验的 A/B 差异建立在“基线无队列索引”的前提上；它衡量的是补齐缺失索引与分页方式，不是调优一个已索引的生产系统。

## 6. 失败与返工

1. 首次试跑用了共享 PostgreSQL 容器（1 CPU、512 MB），所有查询 10 秒以上，数据不可用；改为专用容器（2 CPU、2 GB、`shared_buffers=512MB`）后重跑。
2. keyset 游标写错（用第 N 页第一行作 `<` 游标），B 组的第 2500 页查询返回 0 行；修正为“上一页最后一行”，并把错误批次保留在 `invalid-cursor-v1/`，重跑 B 侧 11 轮。
3. 重复领取按“工单+revision”去重，导致两步领取的覆盖写被计成不同代，重复数为 0；改为按工单去重（补给时清除），旧批次保留在 `invalid-dup-v1/`，重跑 3 轮。
4. 基线最初固定抢队首，50 座席互相踩踏到 0.15 次/秒，不符合真实“从首页挑一条”；改为从首页 20 条随机挑一条，基线 3.7 次/秒。

## 7. 边界

单机、独立 PG（2 CPU/2 GB）、合成工单（按 ECD 意图分布生成 priority/created_at）、无网络、无认证；W2 的补给循环会重置状态并把 `revision+1`，属于实验手段。所有数字只适用于该配置，不外推生产。
