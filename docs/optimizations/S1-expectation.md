# S1 预期（开跑前提交，2026-11-02）

本文件在跑基线前写定，只写方向、机制与失效条件，不写具体提升数字。跑完后原样保留，结果写 `S1.md`。

## 要解决的问题

50 个座席在百万工单里领取“待人工”工单；同时工作台要能翻到队列尾部。当前产品用 CAS 领取（不会重复）与 OFFSET 分页。

## 假设

1. **部分索引**（`WHERE state='waiting_human'`，排序键 `priority DESC, created_at, ticket_id`）使索引只覆盖 5% 的行，列表扫描量与索引体积随待人工比例增长，而不是随全表增长。机制：查询谓词与索引谓词一致时，规划器走 index-only / index scan，避免全表过滤与排序。
2. **keyset 分页**用 `(priority, created_at, ticket_id) < (…)` 代替 OFFSET。机制：OFFSET 需要跳过并丢弃前 N 行，代价随页号线性增长；keyset 直接从游标位置取下一页，代价与页号基本无关。
3. **SKIP LOCKED + 版本号**把 50 座席的竞争从“抢同一行后失败重试”变为“跳过已锁定的行、各自拿到不同行”。机制：单条 `UPDATE ... WHERE ticket_id = (SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1)` 在数据库内完成选取与加锁，减少往返与冲突；版本号保证不会覆盖已变更的行。预期领取吞吐上升、重复领取为 0；代价是不保证严格优先级与公平性，低优先级可能饥饿。

## 预期会看到的形态（不写数字）

- A 基线：深翻页耗时随页号明显上升；50 座席下领取吞吐受行锁竞争与两次往返限制。
- B 优化：深翻页耗时基本不随页号增长；领取吞吐高于 A；重复领取 = 0；索引体积远小于全表索引。
- N 两步领取：会出现重复领取（用于演示），不作为提升对照。

## 失效条件（出现即如实写，不算通过）

- 查询条件与部分索引谓词不一致，规划器不走该索引。
- keyset 期间 `priority` 被修改，导致翻页跳项或重复项。
- SKIP LOCKED 使低优先级工单在 60 秒窗口内长期不被领取（饥饿）。
- 数据库先饱和（CPU、连接、WAL），使 A/B 差异被资源限制掩盖。
- A/A 噪声大于 10%，导致任何差异都无法判定。

## 开跑前声明的口径

- 主指标：50 座席领取吞吐（成功领取/秒），A 与 B 同轮配对。
- 正确性门槛：重复领取 = 0（B 必须；A 也应；N 用于展示非零）。
- 第二主指标：深翻页耗时（5 万待人工、20 条/页、第 1/100/1000/2500 页）。
- 判据：提升需同时超过 10% 与 A/A 噪声的较大者，否则写“无显著收益”。
- 其余指标（p50/p95/p99、跳锁、索引体积、DB CPU/等待）为辅助，不单独用来宣称收益。
