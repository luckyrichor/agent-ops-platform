## 测量边界与资源

- 驱动进程：一次性 systemd 用户单元（CPUQuota=100%、MemoryMax=768M、MemorySwapMax=0），仅本测量单元，结束自动回收；不改产品默认运行。
- PG 会话守卫仅作用于本进程连接：`statement_timeout=5s`、`max_parallel_workers_per_gather=0`；**共享 PostgreSQL 未设本轮整机 CPU/内存限额**，驱动配额不冒充共享 PG 配额。
- 保护采样：测量前/中/后连续只读采样（复用 S3 前置复核控制器模式），53 个窗口内样本，GetAudio/GetVideo /health 全部 200，OOM 增量 0，最低可用内存 4528 MiB。局限保留：健康 GET 不是业务 p95；顾客 memory 服务无只读 HTTP 入口，保护覆盖缺口未消除。
- 语料：本机 20 万确定性合成 bench 商品（20 万全部 active 且可售），无真实用户/真实查询；未下载/重建语料，未触碰其他项目与 9 个停用容器。
- 分位数全部 nearest-rank；warmup 在计时窗口外；各轮数据互不累计（第一次执行存在 db 层跨轮累计口径瑕疵，已修正重跑，两次原始文件均保留）。r2的pool_acquire字段仍是误命名，实际为连接持有时间，见下方勘误。

## 1. 商品详情实体路径基线（方案 A 判定输入）

`CommerceBackend.product(product_id)` 产品原方法（含库存 JOIN、连接池获取），未自造简化 SQL。确定性均匀选真实存在且 active 且可售的 ID（固定步长 667 与总量互素取模，无随机）；并发 2；每轮 warmup 30（窗口外）。

| r1 | 300 | 555.0 | 2.494 | 4.927 | 39.31 | 0 |
| r2 | 300 | 592.4 | 2.534 | 5.754 | 11.29 | 0 |
| r3 | 300 | 924.8 | 2.094 | 2.542 | 2.89 | 0 |

DB 层（每轮独立）：SQL 执行 p50 0.94–1.33ms / p95 1.35–3.88ms；连接持有（checkout→checkin，含执行）p50 1.64–2.05ms。三轮QPS和p99有明显漂移，如实保留，不挑选轮次。其他负载、调度、冷暖等可能原因未做隔离归因，不能据此断言原因。

**判定：product p95 = 2.54–5.75ms，≥ 约 2ms 的门槛。** 按任务分支：不把 A 判为无收益、不放弃 A 作主线候选；极小进程 L1 对照未运行（该对照仅在 p95<2ms 分支要求）；设计 B 作为备选一并提交，本轮等待用户确认，不实施。

`Shopping.graph`（产品真实路径：deterministic Planner、本地角色、memory=None；请求体为中文查询+类目主词+固定预算/区域，非 mock、无固定 sleep）。检索 span 经子类包装 `CatalogSearch.search()` 计时（内部仍真实查库）；每请求恰好 1 条 catalog SQL（limit=100），90 请求/轮×3 轮，并发 2，每轮 warmup 30。

**`CommerceBackend.product` 在导购链路中的实际调用次数：0；贡献：0。** 代码依据：`Shopping.handlers()` 仅注册 catalog/pricing/shipping/recommendation 四个角色（src/agent_ops/shopping.py:26-40），catalog 走 `CatalogSearch.search`，pricing/shipping/recommendation 为纯本地计算（无 DB/模型调用），链路内不存在商品详情调用。本轮测量亦实测每请求恰好 1 条 SQL（90 请求→90 个窗口内 SQL 事件，全部为 catalog 检索），无任何 product 查询。单独的商品详情接口（`access_api` 暴露的 `/v1/commerce/products/{id}`）属另一入口，本轮未测，也未将其计入导购链路。

与生产带模型/memory 请求的差别（未测量，仅说明）：本轮 deterministic Planner 无模型调用，配置为llm planner时增加真实模型调用（可能网络延迟、限流和重试，本轮未测量其耗时）；memory=None 无记忆读写网络调用与幂等写；导购图本身不含下单/库存变更。因此本比值只代表 deterministic 无记忆链路，不能外推生产端到端延迟结构。

## 4. 未验证与失败项

- 正式 S3 缓存矩阵、Redis、进程 L1（含安全语义的元数据缓存+实时库存/价格/状态读取）、singleflight、负缓存、写后失效：全部未实施未运行。
- 真实查询分布未知：bench 语料与 30 条固定查询均为合成，本报告所有结论为模拟条件下的结果。
- A/A 噪声未建立（本轮 3 短轮只观察抖动，不是配对 A/A）；不能据本轮数字宣称任何缓存收益。
- 第一次执行存在 db 层跨轮累计口径瑕疵（逐请求主指标不受影响），修正重跑；两份原始文件均保留，见证据目录 README。
- 保护探针口径限制（健康 GET≠业务 p95、memory 无只读入口）与共享 PG 无整机限额的归因限制均保留。

## 6. 数字溯源与测量勘误

| 报告数据 | 原始字段与计算 |
|---|---|
| 详情/检索三轮p50/p95/p99 | measurement-gate-r2.json → phases.product/catalog.rounds[i].per_request[].latency_ms，升序第ceil(N×q/100)项 |
| 导购总耗时、检索span | phases.shopping.rounds[i].per_request[].e2e_ms / retrieval_span_ms，分别求nearest-rank |
| 导购检索占比 | 每请求retrieval_span_over_e2e，再求均值/范围；原时延三位、比值四位小数，有舍入误差 |
| SQL次数/执行时间 | 各轮db.sql_events_in_window / sql_exec_ms_raw；不包含全部探活/服务端SQL |
| 连接持有时间 | r2的db.pool_acquire_ms_raw实际是checkout→checkin（误命名），不是获取等待；最终脚本改名pool_hold |
| 保护统计 | host-metrics-r2.json → samples中的vmstat、mem_available_mib、protect_probes；窗口内样本按原秒级时间界限筛选 |

Codex独立复算全部9轮的请求数、错误数、分位数、SQL次数和逐请求比值（按舍入区间），通过。第一次执行的跨轮DB累积不用于DB层结论；原始r1、r2均不修改，精确执行源码快照归档，hash与raw fingerprint逐一对应。最终脚本另修正持有时间字段、精确Unix窗口边界、证据防覆盖、无效phase拒绝和异常清理；未触发且未经验证的L1分支从脚本移除，未实施该对照。

旧r2窗口UTC字符串只有整秒精度，只证明整次运行测前/中/后采样，不能声称每个亚秒product子窗口都有采样点。最终脚本独立复跑新增精确Unix时间与实时健康失败停机控制，结果另列，不覆盖或挑掉较慢尾样本。历史326个测量/报告文件hash核对未改。
