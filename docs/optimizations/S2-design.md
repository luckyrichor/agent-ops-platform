# S2 多副本幂等与支付回调去重：预期与设计（待确认，未开跑）

2026-11-03，Codex。本文只写假设、口径与实验设计，不写具体提升数字。

## 1. 现状（事实）

- 工单创建/变更幂等：`support.idempotency_keys(scope,key)` 主键 + `request_hash` + `response_snapshot`；`support.operations(scope,key)` 主键 + `request_hash` + `response`，在同一事务里占位与完成（`workbench.py` 的 `_reserve`/`_finish`）。
- 支付通知：`payments.notifications` 以 `notification_id` 为主键，写入 `payload_hash`；同 ID 不同摘要返回 `PAYMENT_NOTIFICATION_CONFLICT`，重复成功不会回退订单或库存（`payments.py:100-124`）。
- 退款：`refunds.refund_no` 主键、`order_id` 唯一；订单/库存/审计在同一事务。
- **过期：当前 support/payments 的幂等与通知记录没有 TTL 字段**（migration 0005/0006）。7 天有效期只存在于 agent-memory SDK 的幂等记录（P7 文档）。如果 S2 要按 7 天过期，需要新增行为，不是“现有”。

## 2. 基线定义

| 组 | 实现 | 用途 |
| --- | --- | --- |
| **A 基线** | 产品当前实现（上述数据库幂等与唯一约束） | 所有对照的比较对象 |
| **N 演示** | 仅测试用的“进程内字典”幂等开关 | 只演示重复处理后果，不参与提升倍数 |
| **B 候选** | 仅当 A 暴露缺口时才做：补唯一约束/摘要校验/TTL 清理 | 与 A 同轮配对 |

若 A 已经满足全部正确性门槛，S2 的结论就是“无需改动，验证通过”，不为了产出而改代码。

## 3. 假设与失效条件（不写具体数字）

- **假设 1**：数据库唯一键 + 请求摘要能在多进程下阻止重复工单；进程内字典在多进程下失效（演示组会重复）。
- **假设 2**：`notifications(notification_id, payload_hash)` 的冲突检测能让同一通知重复投递只入账一次；同 ID 不同载荷必须拒绝，而不是静默覆盖。
- **假设 3**：把订单、库存、支付、审计放在同一事务里，重复投递不会再次扣库存或回退状态。
- **假设 4**：退款以 `refund_no` 唯一键去重，重放不产生第二次退款。

失效条件：唯一约束缺失或只在前端去重；摘要算法把不同载荷算成同一值；事务边界把审计/库存拆到事务外；锁顺序不一致导致死锁（应记录并中止，不重试掩盖）；跨进程测试只用了同一连接池。

## 4. 开跑前声明（事后不改）

**正确性门槛（必须先过）**

1. 重复工单数 = 0（同一 Idempotency-Key + 同一请求体，200 并发、30% 重复）。
2. 重复入账 = 0（同一 `notify_id` 连续投递 5 次）。
3. 重复退款 = 0（同一 `refund_no` 重放）。
4. 重复请求返回同一结果（响应体与首次一致；同键异体返回 409/冲突码）。
5. 跨进程：两个 API 实例同时处理同一键，仍满足 1–4。

任一项不为 0/不满足，S2 不算通过，先修再测。

**主指标**：在 200 并发、30% 重复请求下，工单创建的吞吐（成功创建/秒）与 p95 延迟；正确性门槛优先于吞吐，正确性不过不报吞吐结论。

**辅助指标**：冲突率、锁等待、通知表行数、审计条数、退款状态机转移次数、TTL 边界行为。

## 5. 场景

1. **工单创建去重**：200 并发，30% 客户端重放同一 `(scope,key)`；同一键同体应只建一张工单，同键异体 409。A 跑 5 轮，N 跑 3 轮（演示）。
2. **支付回调重放**：同一 `notify_id` 连续 5 次；订单只入账一次、库存只扣一次、审计只一条 `PAYMENT_CAPTURED`；第 2–5 次返回成功且不改变状态。5 轮。
3. **退款重放**：同一 `refund_no` 重放 5 次；`refunds` 一行、订单状态只变一次。5 轮。
4. **跨进程**：两个 API 实例（同库），同一键并发；验证 A 与 N（N 预期重复）。
5. **TTL 边界**：当前无 TTL。若确认需要 7 天：新增过期字段与清理任务，测 6 天 23:59、7 天整、7 天 +1 秒；过期后同键应重新执行还是返回“已过期不可重放”，在方案里先定语义，不能两种都算通过。若不新增，S2 记录“无过期，长期保留”的事实与风险。

## 6. 支付通知的签名与沙箱边界

- 压测与回放使用**本地生成的 RSA 2048 测试密钥对**（`.local/s2/keys/`，600 权限），直接构造 `PaymentConfig` 的验证公钥与签名私钥；不调用支付宝沙箱、不使用真实支付宝公钥、不发起任何外部请求。
- `.local/payment-notices/` 里的真实通知只做**离线重放**：校验解析、幂等键、金额/状态机与审计；不回传支付宝、不联网。
- 通知字段只出现在私有目录与私有日志；公开报告只给统计与固定错误码。
