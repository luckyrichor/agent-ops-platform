# S2 预期（开跑前提交，2026-11-03）

只写方向、机制与失效条件，不写具体提升数字；跑完写 `S2.md`。

## 被优化的方案

数据库唯一约束 + 请求摘要已经是正确且简单的幂等方案。候选优化是在它前面加**进程内结果缓存**（命中直接返回首次结果），减少 30% 重复请求带来的数据库往返；不是替换唯一约束。

## 机制假设

1. 短时间内的重复请求大量落在同一进程，缓存能减少 `idempotency_keys`/`operations` 查询与事务开销，降低创建 p95。
2. 缓存只存成功结果，键为 `(scope, key, request_hash)`；同键异体不命中，必须走数据库冲突路径。
3. 跨进程不共享缓存，因此缓存失效后仍由数据库唯一约束兜底；重启只影响命中率，不影响正确性。
4. 支付/退款/通知去重不设 TTL，靠业务唯一约束；通用请求幂等键新增 24 小时 TTL（可配置），过期后同键重新执行，旧结果不得覆盖新结果。

## 预期形态（不写数字）

- 若重复请求集中在短窗口、同一进程：缓存可能降低 p95、提高吞吐。
- 若重复请求分散或并发很高：缓存命中率低、甚至增加内存与失效成本，**可能得到“无显著收益”**；这不是失败，按实写。
- 跨进程重复请求不会命中对方缓存，正确性仍由数据库保证。

## 失效条件

- 缓存键漏掉 `request_hash`，同键异体会命中错误结果。
- 缓存了失败/拒绝结果，或把“进行中”当成功返回。
- 过期键重新执行后，旧请求的延迟完成覆盖新结果（必须有 request_hash 守卫）。
- 缓存无上限或无淘汰，200 并发下内存膨胀。
- 两个 uvicorn 实例共享同一数据库但使用不同连接串/账户，导致唯一约束不生效。

## 正确性门槛（先于吞吐）

重复工单 = 0；重复入账 = 0；重复退款 = 0；重复请求返回同一结果；同键异体返回冲突；跨进程仍满足以上。任一不满足，S2 不算通过。
