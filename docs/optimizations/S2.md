# S2 多副本幂等与支付回调去重

2026-11-03，Codex。数据：`docs/measurements/2026-11-03-s2/`。预期：[S2-expectation.md](S2-expectation.md)，设计：[S2-design.md](S2-design.md)。

## 1. 结论

**数据库唯一约束 + 请求摘要已经足以保证多副本幂等；在其前面加进程内结果缓存没有显著收益。** 同一脚本、两个 uvicorn 实例、200 并发、154 唯一键 + 46 重复（重复占全部请求 23%；46/154≈29.9% 为另一口径，见 §4 更正），六轮全部 0 重复工单；缓存组吞吐中位 152.3 次/秒，基线 140.8 次/秒（+8.1%），p95 1,172 vs 1,270 ms（−7.7%），均未超过 10% 判据，按“无显著收益”记录，不进入主线。注意：吞吐为该批 200 请求约 1.3 秒短突发的完成率，不是持续饱和 QPS。

## 2. 改动

- migration 0010：`support.idempotency_keys` 与 `commerce.idempotency_keys` 增加 `expires_at`（默认 24 小时，`AGENT_OPS_IDEMPOTENCY_TTL_SECONDS` 可配，60 秒–7 天）与过期索引。
- 工单创建与下单：到达过期时间后原子刷新幂等记录并重新执行；完成写入带 `request_hash` 守卫，旧请求的延迟完成不会覆盖新结果。
- 支付、退款、通知去重不设 TTL，靠业务唯一约束（订单号、退款请求号、支付宝交易号/通知 ID）。
- 候选（仅 bench 层）：进程内结果缓存，键为 `sha256(key + 请求体)`；只缓存成功结果，不跨进程共享。

## 4. 性能结果（两个 uvicorn 实例，200 并发）

| 组 | 吞吐 次/s（中位） | p50 ms | p95 ms | 重复 |
| --- | ---: | ---: | ---: | ---: |
| 基线（数据库幂等） | 140.8（139.3 / 140.8 / 164.9） | 783 | 1,270 | 0 |
| 进程内缓存 | 152.3（137.2 / 152.3 / 157.9） | 687 | 1,172 | 0 |

> 2026-11-03 复核（CodeBuddy）：本表括号内逐轮数字曾误写为 141.7 / 157.6 / 148.7（基线）与 137.2 / 157.9 / 152.3（缓存）排序。已按原始 `docs/measurements/2026-11-03-s2/v2-base-1..3.json`、`v2-cache-1..3.json` 重算更正：基线 139.27 / 140.83 / 164.86，缓存 137.24 / 157.86 / 152.29。中位数 140.8 / 152.3 及 p50/p95 与结论（+8.1%、−7.7%，均未超 10% 判据）不变。原始 JSON 未改动。

**机制证据**：200 个请求同时发出，46 个重复请求与首次请求并发到达，两个实例的缓存统计均为 `hits=0 / misses=100`（每个实例 100 个请求）。缓存对“并发重复”无效——重复请求在首个请求完成前就已到达，缓存里还没有结果。服务耗时占总请求耗时约 99.99%（51.96 vs 51.96 秒），说明本路径几乎全部时间在数据库事务，缓存命中一次才能省下这部分，但本场景一次都没命中。

> 2026-11-03 返修更正（CodeBuddy，按 Codex 验收意见）：
> 1. **重复占比口径**：旧轮次 46 重复 / 200 请求 = 23%（占全部请求）；46/154≈29.9% 是相对唯一键的口径，两者都不是“30% 请求重复”的准确表述。若后续设计要求 30% 请求重复，应使用 140 唯一 + 60 重复并写入新批次，不覆盖旧证据。
> 2. **吞吐口径**：`throughput_per_second` 只表示这批 200 并发请求（约 1.3 秒突发）的完成率，不是持续饱和 QPS，不得用于容量规划或持续吞吐结论。+8.1% 差异未做统计显著性检验，只能说“未超过预设 10% 收益阈值”，不能泛化为“证明无收益”。
> 3. **TTL 守卫边界**：旧 TTL 测试是“先等第二次请求完成，再尝试旧完成写入”的顺序时序，0 行主要因为 `response_snapshot` 非空；`request_hash` 对同一请求体的跨代重算结果相同，不是代际令牌。真实实现以同事务 `FOR UPDATE` 行锁串行化完成写入，可排除已观察到的跨代覆盖窗口，但“所有迟到请求场景已覆盖”的说法不成立：并发时序竞态测试仍缺（见 §8），现有测试只能声称覆盖了受控顺序时序。核心事务未按本条意见改动。

因此吞吐 +8.1%、p95 −7.7% 都不超过 10% 判据，判为无显著收益；要真正解决并发重复，需要 singleflight（合并同键进行中的请求），那是另一个方案，本轮未测。

## 7. 代价与失效条件

- 缓存键漏掉请求体哈希会返回错误结果；只缓存成功结果，进行中/失败不缓存。
- 缓存不跨进程、不跨重启；命中率低时只有额外内存与查找开销。
- TTL 过期后同键重新执行，旧结果不得覆盖新结果；依赖 `request_hash` 守卫，若移除守卫会退化为覆盖。
- 支付/退款不设 TTL，记录长期保留；需要单独的归档/清理策略，本实验未做。
- 工单事件表是 append-only，测试重置无法删除历史；本轮用“每轮时间窗”统计重复，没有物理清理。**S2 已跑轮次状态可能不完全干净**；后续改为模板库克隆。
