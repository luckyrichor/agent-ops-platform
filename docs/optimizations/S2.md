# S2 多副本幂等与支付回调去重

2026-11-03，Codex。数据：`docs/measurements/2026-11-03-s2/`。预期：[S2-expectation.md](S2-expectation.md)，设计：[S2-design.md](S2-design.md)。

## 1. 结论

**数据库唯一约束 + 请求摘要已经足以保证多副本幂等；在其前面加进程内结果缓存没有显著收益。** 同一脚本、两个 uvicorn 实例、200 并发、30% 重复请求，六轮全部 0 重复工单；缓存组吞吐中位 152.3 次/秒，基线 140.8 次/秒（+8.2%），p95 1,172 vs 1,270 ms（−7.7%），均未超过 10% 判据，按“无显著收益”记录，不进入主线。

## 2. 改动

- migration 0010：`support.idempotency_keys` 与 `commerce.idempotency_keys` 增加 `expires_at`（默认 24 小时，`AGENT_OPS_IDEMPOTENCY_TTL_SECONDS` 可配，60 秒–7 天）与过期索引。
- 工单创建与下单：到达过期时间后原子刷新幂等记录并重新执行；完成写入带 `request_hash` 守卫，旧请求的延迟完成不会覆盖新结果。
- 支付、退款、通知去重不设 TTL，靠业务唯一约束（订单号、退款请求号、支付宝交易号/通知 ID）。
- 候选（仅 bench 层）：进程内结果缓存，键为 `sha256(key + 请求体)`；只缓存成功结果，不跨进程共享。

## 3. 正确性结果

| 场景 | 结果 |
| --- | --- |
| 200 并发、154 唯一键 + 46 重复、两实例 ×6 轮 | 每轮 154 张工单，重复 0，全部 HTTP 200 |
| 无幂等演示（单进程两连接池） | 182 请求 → 182 张工单，重复 42 |
| TTL 未过期（1 小时） | 同键返回同一工单 |
| TTL 到达边界（`expires_at = now()`） | 视为过期，重新执行并生成新工单 |
| TTL 过期后 | 重新执行、`expires_at` 刷新 |
| 支付回调 5 次重放 | 只入账一次（现有测试，本地临时 RSA 密钥，不联网） |
| 退款重放 | 只产生一次退款（现有测试） |
| 同 `notify_id` 不同签名内容 | 拒绝（现有测试） |

## 4. 性能结果（两个 uvicorn 实例，200 并发）

| 组 | 吞吐 次/s（中位） | p50 ms | p95 ms | 重复 |
| --- | ---: | ---: | ---: | ---: |
| 基线（数据库幂等） | 140.8（141.7 / 157.6 / 148.7） | 783 | 1,270 | 0 |
| 进程内缓存 | 152.3（137.2 / 157.9 / 152.3） | 687 | 1,172 | 0 |

**机制证据**：200 个请求同时发出，46 个重复请求与首次请求并发到达，两个实例的缓存统计均为 `hits=0 / misses=100`（每个实例 100 个请求）。缓存对“并发重复”无效——重复请求在首个请求完成前就已到达，缓存里还没有结果。服务耗时占总请求耗时约 99.99%（51.96 vs 51.96 秒），说明本路径几乎全部时间在数据库事务，缓存命中一次才能省下这部分，但本场景一次都没命中。

因此吞吐 +8.2%、p95 −7.7% 都不超过 10% 判据，判为无显著收益；要真正解决并发重复，需要 singleflight（合并同键进行中的请求），那是另一个方案，本轮未测。

## 5. 资源限制与环境

- 每个实例：`taskset -c 0-1`、`RLIMIT_AS=1 GiB`、`nofile=4096`。
- **S2 早期轮次未加 cgroup 配额**，标注“保护不完整”。收尾新增 `scripts/s2-round.sh`：每轮从模板库克隆新库、两个实例跑在 systemd user scope（CPUQuota=100%、MemoryMax=512M、MemorySwapMax=0），并记录 `MemoryPeak`/`CPUUsageNSec`。验证轮：200 请求全部 200、142.2 次/s、p50 837 ms、p95 1,261 ms，两实例峰值内存约 69 MB、CPU 各约 1.23 秒；轮末删除克隆库。保护服务探针（GetAudio/GetVideo/memory p95）尚未接入。
- 数据库：S1 专用 PostgreSQL（2 CPU、2 GB、`shared_buffers=512MB`）。

## 7. 代价与失效条件

- 缓存键漏掉请求体哈希会返回错误结果；只缓存成功结果，进行中/失败不缓存。
- 缓存不跨进程、不跨重启；命中率低时只有额外内存与查找开销。
- TTL 过期后同键重新执行，旧结果不得覆盖新结果；依赖 `request_hash` 守卫，若移除守卫会退化为覆盖。
- 支付/退款不设 TTL，记录长期保留；需要单独的归档/清理策略，本实验未做。
- 工单事件表是 append-only，测试重置无法删除历史；本轮用“每轮时间窗”统计重复，没有物理清理。**S2 已跑轮次状态可能不完全干净**；后续改为模板库克隆。

## 8. 未验证

1. cgroup CPU/内存配额未加，同机保护不完整。
2. 支付回调只做服务层与现有测试，没有走两个 uvicorn 的 HTTP 端到端重放。
3. 24h+1s 未单独跑（已覆盖未过期与正好到期）。
4. 旧请求延迟完成不覆盖新结果只有代码守卫，缺少并发时序测试。
5. 缓存命中率未单独测量，无法判断在“重复集中在同一实例”时是否有收益。
6. 200 并发只跑短时突发，没有持续稳定性与 p99。
7. 数据库重置不完整（append-only 事件），跨轮状态会累积；已用时间窗规避统计，但资源状态不完全干净。
