# P9 补充能力方案：开环压测与 5000/10000 SSE 可行性（待批准，未实施）

2026-11-02，Codex。本文只是方案与估算，**没有改代码、没有开跑**。两项能力都通过后才用于 P10 的 S4/S6。

## 一、开环模式（固定到达速率）

### 目标

现有生成器是闭环：N 个 worker 完成一个再发下一个，服务变慢时自然降速，测不出“过载时会发生什么”，也会低估排队延迟（coordinated omission）。开环按固定速率发请求，不等响应。

### 设计

- `--mode open-loop --rate R`：第 i 个请求的计划发送时刻 = 起点 + i/R；到达即发，不等前一个完成。
- 每个请求记录三个时间：计划时刻、实际发出、收到首帧/完成。**发送滞后**（实际-计划）本身就是客户端饱和信号。
- 在途上限 `--max-in-flight`（默认 4×R），超过即记录 `client_backpressure` 并停止升速，避免生成器自己 OOM。
- 请求超时独立于节奏；超时计入错误，不重试。测量口径为“从计划时刻起算的完整延迟”，因此包含排队。
- 输出：提供速率、实际完成速率、发送滞后 p95、在途峰值、完整延迟分位、错误分类。

### 实验用法（S4 需要）

- 稳态 200 并发等价的到达率，先跑 60 秒基线，再注入 120 秒模型故障（慢 10 秒、429、5xx、断连），观察进行中请求、事件循环延迟、非模型接口 p99、恢复时间。
- 过载档：从 1×容量逐步加到 1.5×/2×，记录吞吐平台、错误率与延迟拐点。

### 失效条件与自检

- 生成器 CPU >70%、发送滞后 p95 >5%、在途达到上限 → 该轮标“生成器饱和”，不能归因于 SUT。
- macOS 单源端口：开环 200 req/s × 30 秒 = 6000 连接，仍在 16k 临时端口内；更高要复用连接或加源地址。
- 闭环与开环结果不合并报告，基线仍以闭环为准。

## 二、5000/10000 SSE 连接可行性爬坡（只做传输）

### 前提

只跑 `/bench/hold` fixture，不经过模型与数据库；业务 1000 档已经通过（1000/1000、首帧 p95 130–135 ms、0 错误）。本轮回答“同一台机器能挂多少条 SSE”，不回答“能服务多少业务请求”。

### 档位与节奏

1000（已有）→ 2000（可选）→ 5000 → 10000。每档先做一次 60 秒演练（只验证建立/清理），无异常才做 3 次完整运行；任何一档触发硬闸即停止，不再升档。

### 资源估算

**文件描述符**

- SUT 下限 ≈ `N + baseline(~40) + margin`；10000 连接需 ≥10050，设 `LimitNOFILE=32768`（软硬一致），并核对 `/proc/sys/fs/file-max`、`file-nr`。
- 生成器同样需要 N 个 socket + 监控余量；macOS 进程软限制要显式 `ulimit -n 20480`，硬限制当前 unlimited。
- 反向代理不参与本轮；若将来加 nginx，需另加约 N 个上游 socket 与 `worker_connections`。

**端口**

- 单源 IP 到同一 `IP:port` 的四元组最多用尽可用临时端口。macOS 临时端口约 16k（49152–65535）。
- 10000 连接一轮会留下约 10000 个 TIME_WAIT（60 秒内），**连续两轮可能耗尽**。对策：轮间至少间隔 90 秒；或绑定第二个源地址（Mac 已有 192.168.1.12 与 Tailscale 地址）分摊；不靠调小 TIME_WAIT 解决。

**内存**

- 每连接：应用状态 16–64 KiB + socket 实际缓冲 32–128 KiB。
- 5000：0.24–0.96 GiB；10000：0.48–1.85 GiB，另加基础 150 MiB。
- 宿主当前可用约 5 GiB，但 bench slice `MemoryMax=2 GiB`。10000 档可能撞上限：先测 1000/5000 的每连接增量，线性外推；若 10k 预计超过 1.8 GiB，则标“预算不足未执行”，不临时放宽。

**CPU**

- 心跳 0.2 秒/连接：10000 连接约 50k 帧/秒，单进程 asyncio 很可能先撞 CPU 而不是内存。预计 5000 是拐点，本轮的意义就是找到它。

### 同机保护

- bench 全部进程（SUT、桩、监控）进同一个受限 slice：CPUQuota 125%、MemoryHigh 1.5 GiB、MemoryMax 2 GiB、MemorySwapMax 0、TasksMax 512；先验证 cgroup 委派生效，否则不跑。
- 保护对象：GetAudio、GetVideo（API 与 AI worker）、agent-memory。只读探针每 5 秒一次，记录 p95；连续 3 个窗口比本次背景基线差 10% 即中止。
- 硬闸：MemAvailable <2 GiB、slice 达 MemoryHigh 持续 5 秒、OOM/OOM-kill 增长、持续 swap-in/out、保护服务探针连续失败——任一命中立即停止并排空连接。
- 只在非高峰窗口跑；期间不做下载/转码/其它压测；结束后核对 TIME_WAIT 与内存回落。

### 判据

- 每档结论只写“在这一档、这个窗口、这台机器上”的建立成功率、健康首帧 p99、RSS、FD、CPU、事件循环延迟。
- 退化点要归因到 CPU / 内存 / FD / 端口之一；不能归因的写“未定位”。
- 10000 未跑或中途停止，如实写“未验证”，不用 5000 的结果外推。

## 三、实施顺序（待批准后）

1. 生成器加开环模式与发送滞后统计，离线单测覆盖节拍、在途上限、客户端背压。
2. 生成器加连接爬坡与 FD/端口自检；SUT 侧加 cgroup 预算与服务探针。
3. 1000 演练复验 → 2000 → 5000 → 10000，每档单独报告。
4. 开环先用于 S4 的故障注入前置演练（仅验证工具），再进入正式 S4。

## 四、需要批准的点

- 是否按上述档位与硬闸执行 5000/10000；`MemoryMax=2 GiB` 是否维持（维持则 10k 可能判预算不足）。
- 是否允许测量期间占用非高峰窗口与 125% CPU 配额。
- 开环的到达率档位（默认 1×/1.5×/2× 当前容量）。
